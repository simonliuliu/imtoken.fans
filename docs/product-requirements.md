# imToken Fans 产品需求说明

版本：v1.0 · 更新：2026-10-15 · 范围：四板块首版及后续方向。

本文件把用户本轮需求转成后续设计、开发与验收依据；不表示相关功能已经实现。执行顺序见 [路线图](../roadmap.md)，代码现状与技术边界见 [执行计划](product-execution-plan.md)，本轮记录见 [需求对齐任务](tasks/product-scope-alignment.md)。

## 1. 产品目标与决策口径

imToken Fans 是服务 imToken 钱包用户的社区：通过安全经验降低使用风险，通过反馈和共创改善产品，通过讨论与活动形成持续参与。

| 用户已明确的需求 | 本文采用的产品定义 |
| --- | --- |
| 钱包安全：官方和用户都能分享安全故事、案例 | 钱包安全以故事、案例为核心，辅以指南、提醒与问答；明确发布者与内容来源 |
| 产品共创包含反馈、用户产品、官方更新 | 一级名称为「产品共创」，下设「产品反馈 / 社区产品 / 产品公告」；子区暂用「社区产品」以减少同名歧义 |
| 反馈参考 Canny，支持投票、讨论、合并归类 | 首版必须支持分类、人工合并与处理闭环；自动相似推荐和 AI 聚类分阶段增强 |
| 用户提交自己做的产品，类似 Product Hunt | 支持作品展示、访问入口、支持票和创作者交流；不限于 AI 产品 |
| 综合交流先做论坛，可聊炒币行情 | 首版文本/图片/评论/标签；$BTC、PnL、代币 agent 可做隔离演示，真实交易能力后置 |
| 活动区是公告和活动入口 | 首版可发布活动、看详情并进入真实参与入口，复用已有签到抽奖 |

「社区产品」名称、反馈状态词、首版排序规则等是本文建议默认值，可在下一轮界面 review 时调整。用户没有指定上线时间、运营人员、官方关系或回应时效，本文不替其作出承诺。旧文档中「产品反馈」作为一级板块、AI 专属共创和合并后置的规划由本文件更新；历史设计与 review 保留原貌。

## 2. 信息架构与关键用户路径

```text
首页
├─ 钱包安全：安全故事 / 案例分析 / 指南提醒 / 求助问答
├─ 产品共创
│  ├─ 产品反馈：问题 / 建议 → 支持与补充 → 归类/合并 → 处理 → 更新与验证
│  ├─ 社区产品：提交作品 → 审核 → 展示 → 支持/试用/交流 → 迭代
│  └─ 产品公告：授权发布 → 版本更新/公告详情 → 关联反馈
├─ 综合交流：钱包经验 / 币圈行情 / 行业讨论 / 其他交流
└─ 活动区：活动公告 → 规则详情 → 参与入口（含既有签到与抽奖）
```

首页采用内容列表方向；按 2026-10-15 第二轮首页 review，四板块入口仅保留在导航，正文去掉重复入口卡片与板块筛选。顶部用一个推荐轮播承载热门文章、活动或社区产品，配合精简热门列表；下方聚合近期内容，保留明确的发布操作。整体克制、可读，不堆叠功能介绍与成长大卡。首页推荐/最新/热门聚合四板块公开内容：推荐仅取管理员标记推荐的帖子并按发布时间倒序，最新按发布时间倒序，热门按评论数倒序、同数按发布时间倒序；推荐不由点赞或支持数自动决定，也不因轮播曝光改变顺序。当前本地演示字段用于预览该规则，正式内容查询及后台推荐权限仍在后续真实模型任务中实现。首页顶部热门采用相同评论数口径。各板块采用适合自身任务的列表、筛选和详情；反馈处理状态不应用于安全故事、社区产品或活动。全站发布先选内容类型再呈现相应字段，产品公告和活动公告只向有权限的人员开放。

普通用户的核心路径：看案例并讨论；先查已有反馈再提交/支持并追踪结果；浏览社区产品并与创作者交流；发起行情讨论；查看活动规则并参与。运营路径：审核内容、整理反馈、维护可信来源、发布活动；产品处理人员负责分派、状态和处理说明。

## 3. 钱包安全

| 编号 | 首版要求 | 验收标准 |
| --- | --- | --- |
| SAFE-01 | 官方/用户分享故事和案例，兼容指南、提醒、问答 | 均可列表浏览、打开详情；按类型和来源筛选；普通用户不能伪造官方发布身份 |
| SAFE-02 | 表单包含标题、正文、类型、标签、可选图片及参考来源 | 故事可描述经过/识别信号/经验，案例可写手法/风险/防范；不强制每条内容填所有栏目 |
| SAFE-03 | 评论回复、点赞、举报、运营置顶 | 与通用治理一致；用户故事、运营整理、来源核验、官方发布有可辨认标识 |
| SAFE-04 | 对紧急安全问题提供可信求助指引 | 入口由运营确认；明确社区公开讨论边界，疑似漏洞和进行中的盗损引导到受控渠道，不要求公开补充敏感证据 |

发布提示要求遮挡助记词、私钥、密码、地址和交易截图中的敏感信息；不要求提供资产余额或损失截图作为发帖条件。身份来源和事实核验分开：官方人员发文不等于所有案例均已验证，用户自述也不因缺乏核验直接变成虚假。对可疑链接提供风险提示，避免案例正文成为诈骗入口。

## 4. 产品共创：产品反馈

2026-10-16 用户细化：产品反馈以 IDEA 为主要交互对象，论坛用户可提交、投票、评论和回复；每条评论（含回复）也接受独立投票，按用户去重且可取消。论坛 Admin 可编辑与标记 IDEA 和评论，保留原作者、修改记录和修改标识。人工确认同质 IDEA 后，以该组最先提交的 IDEA 为主（时间相同时以稳定 ID 决定），支持人数按用户集合去重，原文/评论来源及旧链接保留；误合并可撤销。上述作为本节首版补充，不取消视频文件、权限、审核、通知及历史数据要求。交互原型与真实业务验收分开，见 [IDEA 原型任务](tasks/cooperation-idea-preview.md)。

### 4.1 收集、发现与支持

| FB-01 | 问题/建议分型，标题、描述、使用场景、产品模块 | 问题可按需填写复现步骤、预期/实际表现、版本/系统/网络；建议填写目标和当前困难，不强制填问题专用字段 |
| FB-02 | 关键词查找已有反馈，模块/类型/状态筛选，最新/支持数排序 | 创建入口提供搜索已有反馈的路径；可直接支持并补充已有问题；搜索仅返回当前用户可见记录 |
| FB-03 | 图片及视频文件上传 | 能上传实际视频文件、显示进度/失败重试并播放；校验归属、格式、大小/时长、审核前可见性和清理；仅有视频外链不算完成 |
| FB-04 | 一人一条支持票、可取消、评论回复 | 数据库唯一约束与幂等写入；刷新计数正确，重试不重复；旧愿付费/创意票不计入新支持票 |

| FB-06 | 状态/结果通知与公告关联 | 提交者、支持者可获相关更新；取消支持后停止基于该支持的后续通知；另有订阅或作者身份时继续接收；同一事件按人去重 |
| FB-07 | 人工合并重复反馈，保留来源与可追溯性 | 按下节场景验收；不能只增加「重复」标签便宣称完成 |

首版搜索提供可用的关键词匹配与过滤；自动输入联想、语义检索、跨语言相似推荐可后置。内容本身不强制自动翻译，界面仍需中英双语。

### 4.2 归类与合并规则

归类解决「都与交易确认有关」，合并解决「同一版本同一场景下的同一问题」。同模块的不同网络、不同根因、不同目标可关联而不合并。首版由运营/产品处理人员确认，AI 仅作为后续候选建议，不能直接覆盖用户诉求。

建议合并流程：选择来源及目标 → 查看摘要、票数重叠、评论/附件与可见性 → 填原因并确认 → 同一事务建立合并记录及支持映射 → 通知相关用户 → 保留原链接和合并说明。只能把公开且同权限范围的反馈合并到公开主反馈；私密/未审核材料不因合并而公开。敏感记录须先处理，不能靠合并绕过审核。

| 必测场景 | 预期结果 |
| --- | --- |
| A 有甲乙支持，B 有乙丙支持，A 合入 B | 有效支持者为甲乙丙，共 3 人；不将 2+2 算成 4；按用户集合计数 |
| 合并后访问 A 的旧链接 | 展示合并说明并可进入 B；原作者、原文、评论、附件和来源仍可追溯，已隐藏内容保持原权限 |
| 合并后的讨论和新投票 | 新互动指向主反馈；历史评论保留原父子关系和来源，避免静默丢失或串错回复 |
| 甲在合并后的主反馈取消支持 | 移除甲在该合并组的有效支持，刷新后不被旧来源票重新加回；保留取消操作记录 |
| 并发合并、重复请求或链式 A→B→C | 不循环、自合并或重复计票；解析至同一有效主反馈；失败回滚且保留审计 |
| 撤销一次误合并 | 授权人员可按操作记录恢复原关系/原始支持来源；合并期间的新票和评论保留在其实际目标，不猜测归属；撤销后重新计算并通知 |
| 合并与成长值、通知 | 不因票或评论映射重复发 XP；同事件同收件人一条通知，不重复奖励贡献 |

技术实现可以保留原始记录并增加合并关系/事件；具体 SQL 在模型任务中确定。首版须有受控的撤销合并能力与上述数据恢复规则，不要求首版提供复杂的自助拆分编辑器。

### 4.3 处理状态与优先级

建议状态：待整理 → 评估中 → 计划中 → 进行中 → 已完成；旁支为需补充信息、暂不采纳。合并到其他反馈以独立合并关系表示，不与处理状态混成一个不可恢复的「重复」终态。已完成之后允许用户反馈仍未解决，由处理人员决定重开并记录原因。

审核状态（能否公开）、处理状态（团队在做什么）、官方来源（谁发布）、用户点赞/支持（互动）各自独立。发过一条回应不代表进入计划，已发布更新也不自动等于每位用户的问题已解决。首版由授权人员人工关联版本和标记完成，不以投票数自动触发排期或承诺日期。

排序除最新、支持数外，应保留安全/严重故障的人工优先处理能力。运营判断参考影响范围、严重程度、复现信息、可行性和重复报告，不以持仓或资产规模给用户需求加权。负责人和真实反馈承接流程须在 M3 验收前落实。

## 5. 产品共创：社区产品（Product Hunter）

| 编号 | 首版要求 | 验收标准 |
| --- | --- | --- |
| BUILD-01 | 创作者或团队成员提交已可访问/有可验证 Demo 的产品 | 必填产品名、一句话简介、描述、网址、Logo、至少一张截图、类别、平台、价格、发布阶段和创作者关系；可补充创作者说明及希望获得的反馈；提交后先审核再公开 |
| BUILD-02 | 列表发现与筛选 | 最新发布、近期热门、社区高分三种排序；可按关键词、类别、平台、价格、阶段筛选；高分排序以至少 5 条体验评分作为有效门槛 |
| BUILD-03 | 支持票、体验评分和讨论分开表达 | 登录用户每个产品一张支持票且可取消；非作者确认体验后可给 1–5 星、正文评价及优缺点标签并可编辑；支持数、评分与旧愿付费/创意票独立统计 |
| BUILD-04 | 与 imToken 关系清晰 | 收录钱包、加密社区及相关 AI 产品；社区收录、支持和评分均不代表 imToken 官方出品、推荐、投资或安全背书 |

首版收录服务钱包用户及加密社区的工具、应用和相关 AI 产品，避免变成无边界广告目录；AI 是标签/类别，不是唯一准入条件。单有想法尚无作品可作为「共创想法」在后续扩展，旧 idea 保留历史入口，不伪装成已完成产品或 imToken 功能建议。

首版借鉴「发现作品 → 试用 → 支持/评分/讨论 → 创作者迭代」路径。日榜奖项、定时 launch、付费推广、模拟投资、融资、交易及复杂推荐后置；页面有可用作品比移植完整榜单机制更重要。不得把用户访问外链或点击支持当成已完成试用。

产品公告讲产品变化，活动公告讲参与安排，安全提醒归安全区；可在首页交叉推荐，但只有一条主内容和主归属，避免复制三份导致评论、票数和更新分裂。

## 7. 综合交流与远期探索

| 编号 | 范围 | 首版/后续边界 |
| --- | --- | --- |
| TALK-01 | 标题、正文、图片、标签、列表/详情、评论回复、点赞、举报、置顶 | 首版真实论坛能力；允许币圈和行情讨论，旧 AI 专属审核不得阻断 |
| TALK-02 | $BTC 等代币提及与代币话题 | 可先演示可点标签/代币卡；真实代币识别后续需区分链、合约与同名代币，不以符号唯一定位资产 |
| TALK-03 | 用户 PnL 展示 | 后续可做固定虚构用户和固定样例收益，明确「模拟数据」、统计区间、计价币和计算假设；不得从真实登录资料推断持仓或绑定真实钱包 |
| TALK-04 | 代币 agent | 可展示样例问答/代币信息卡，标注预设回答及示例时间，不冒充实时分析、真实执行或收益预测 |
| TALK-05 | 真实行情、PnL、交易和 agent 执行 | 独立后续立项；本批不接行情服务、不索取交易授权、不开放下单、代管或收益排行 |

2026-10-15 新增「数字币人」入口需求：将首页原「参与社区」卡替换为类似推荐圈子的头像网格，综合交流同步提供入口。先展示 BTC、ETH、NEAR、ZEC、牛来币五个拟人角色及圈子占位预览，头像与性格为展示设定。长期设想是每个币人有性格、自己的圈子并担任管理员，用户在综合交流或圈子中 @ 它后可获回应，币人也可视情况参与圈内讨论，人和币人、币人之间均可交流。本批仅负责入口和占位，由其他负责人实现真实圈子、AI 回复、@ 触发和币人对话；不展示伪造聊天、真实活跃人数或加入成功。后续单独定义上下文、触发与频控、权限治理和负责方接口。牛来币暂以用户给定名称作为占位，不补造 ticker、链或合约。

TALK-02～04 与数字币人运行能力不是四板块首版的发布阻塞项；数字币人入口按独立 M1 小批交付。建议先验证话题和讨论需求；真实 PnL 再定义用户授权、公开范围、成本基础、转账影响、已实现/未实现盈亏和数据完整性。单凭 $BTC 文本、钱包余额或片段交易不能给出真实用户收益。

社区治理处理诈骗、仿冒客服、恶意导流和刷屏；一般行情观点不因与 AI 无关而被拒绝。反对观点可讨论，支持数、等级或 PnL 都不作为真实性背书。

| EVENT-02 | 活动列表、详情及状态 | 未开始/进行中/已结束明确；活动时间与报名截止时间如不同需独立展示，不用浏览器本地时钟作资格判断 |
| EVENT-03 | 参与入口支持站内路径或经核验的外部链接 | 标注跳转目标；点击外链不计为报名成功，不预填名额、奖励或发奖承诺 |
| EVENT-04 | 整合已有签到与券制抽奖 | 保留服务端时间、券余额、库存、次数及幂等控制；无券路径有说明；入口整合不能误算新抽奖系统已完成 |

首版不必自建报名、支付或多活动抽奖引擎。实际存在的报名系统可作为外链接入；后续若需要名额、名单、兑奖，单独定义数据及权限。

## 9. 共享能力、权限与数据边界

板块、内容类型、审核状态、业务处理状态分开建模；可见性、发布者来源、标签也独立。建议概念对象包括内容主记录、反馈扩展、社区产品扩展、公告/版本、活动扩展、媒体、支持关系、合并事件和状态历史；这是概念设计，不表示决定新建同名数据库表。

| 身份/能力 | 允许操作 | 必须限制 |
| --- | --- | --- |
| 游客 | 阅读公开内容、搜索和查看规则 | 看不到未审核/私密材料，不能真实投票/发布 |
| 登录用户/创作者 | 发安全/交流/反馈/本人作品，评论、支持、管理本人内容 | 不可更改处理状态、合并反馈、发布官方公告或操作他人附件 |
| 运营审核人员 | 按授权审核/置顶/举报/整理 | 审核权限不自动包含反馈合并、产品状态或官方发布权限 |
| 产品处理人员 | 按授权归类、分派、合并、更新状态及关联版本 | 不能由 verified 标签自动获得权限；私密信息不可随合并泄露 |
| 公告/活动发布人员 | 按单独权限发布、编辑和撤回对应内容 | 与抽奖规则/库存管理分开授权，全部留审计记录 |

账号、等级、评论、通知、后台和签到抽奖优先复用。迁移保留原始作者、评论回复、互动语义、经验和旧链接；不把旧愿付费/创意票换算成新支持。新增互动的 XP 规则需单独确认，首版不以合并、撤销或重试重复发分。

演示记录与真实业务记录分开；演示发布、点赞、评论、投票、PnL、agent 不调用真实写入、积分或交易流程。非演示的既有登录和访问埋点仍可能正常联网，不能把数据隔离描述成整站离线。

## 11. 产品建议与运营准备

结构方向可行，最大的执行风险是四块同时铺开，却没有人持续处理反馈和维护内容。建议先用安全内容和反馈闭环验证价值，再逐步增加作品供给与活动；不要求四块以相同功能深度同时迭代，但 M5 发布必须有各自真实可用的基本能力。

| 风险/问题 | 建议 | 决策时点 |
| --- | --- | --- |
| 一级和子区都叫产品共创，用户难分「提需求」与「发作品」 | 一级保留用户指定名称，子区展示为社区产品，发布按钮写提交产品/作品 | 下一次界面 review |
| 投票多等于优先级，低票严重问题被淹没 | 支持是需求信号，严重安全问题另有优先处理通道 | M3 状态/运营规则 |
| 太早做自动合并，误合并不同根因，丢票或泄露资料 | 首版人工确认、分类和合并分开、保留来源/撤销/审计 | M3-B 设计与 QA |
| 共创目录变广告区，创作者不回复 | 收录钱包/加密社区相关作品，先招募愿持续迭代的创作者；观察有效回复与迭代，不只看票 | M3-C / 运营准备 |
| 行情和收益榜挤压安全/反馈，示例收益冒充真实 | 行情留在交流区；PnL 演示明确标识，真实收益和交易另立项 | 演示或立项前 |
| 公告无人维护、反馈只有收集没有结果 | 落实反馈承接人、公告来源、处理权限和内部巡检节奏，再考虑对外时效 | M3 / M5 前 |
| 活动引流只带来刷分 | 观察参与后是否阅读/讨论/反馈，不以签到抽奖数代替社区质量 | M4 / 发布后 |

建议指标：安全内容获得可信补充/回复的比例；反馈首次有效处理耗时与覆盖率、合并后唯一参与者、完成后用户验证；社区产品获得有效讨论/创作者回复和迭代的数量；交流帖得到回复的比例；活动参与后的社区留存。先定义口径并观察基线，不预设没有依据的数字目标。
