# 活动限制与标签并发独立安全检查

日期：2026-11-05。候选 `0034_activity_restriction_atomicity.sql` 的 SHA-256：`6ab80a49887bed5ed7a98c3fd6e9df4653751363f995aa22d4c4d9f0ad954bf1`。

## 验证环境与结果

独立 QA 在本机临时 PostgreSQL 16.9 中使用虚构账号、隔离的 auth/storage 替身和 pgcrypto，依次原样应用 0001–0031、论坛反馈候选 0032 和审核候选 0033，再应用上述精确 0034。使用多个独立连接完成 [13 组最终候选检查](activity-restriction-qa.results.json)，全部通过：

- 迁移持表锁期间，旧应用的 INSERT / DELETE 已发起并等待；迁移提交撤权后均以 `42501` 失败。迁移后旧应用继续失败，新受控 RPC 可用。
- 活动与处分竞争时，`READ COMMITTED` 下等待后拒绝，`REPEATABLE READ` 的旧快照以 `40001` 拒绝；签到、抽奖及活动资产保持正确。
- 跨管理员互设标签、并发 upsert/删除、角色权限和目标校验通过；审计失败时标签、guard 和审计均回滚。
- 被拒绝抽奖的经验、徽章、券和库存全部回滚；账号删除与活动交错后，私有 guard 依外键清理。

另一次独立安全审查构造了两个未在仓库基线出现的数据库漂移夹具：旧 `SECURITY DEFINER` 标签写入函数，以及提前跳过签到流水的旧触发器。修复后的候选均拒绝迁移，回滚后没有创建 guard 表，用户、标签、活动、经验、券和审计聚合快照不变。

此前 48 组原型检查包含旧漏洞与不安全锁方案的阳性复现，不能计入最终候选的 13 组。PGlite 16 项、后台 Action 和工程检查另见 [任务卡](../tasks/blacklist-fail-closed.md)。

## 生产边界

本次没有连接正式 Supabase、操作浏览器、写入真实数据或执行正式迁移。隔离 PostgreSQL 的 auth/storage 模型不等于正式 Supabase/PostgREST；正式角色、函数、触发器、动态 SQL、间接调用、可写视图、外部特权写入者及真实账号并发仍需目标库只读预检和人工审计。

迁移只阻断已发现的直接特权函数引用与未知受保护表触发器；可信数据库 owner/超级用户的任意 SQL 可以绕过应用协议，维护写入必须遵循相同锁与 guard 协议。严格活动函数指纹可能因版本或真实结构差异而拒绝迁移，必须调查，不得降低检查。旧应用在迁移后不能修改用户标签，回退须保留兼容 RPC 和历史记录，不盲目恢复直接写权限。
