# 钱包 nonce 单次消费：部署与回退检查

本方案属于 PR #48 草稿，尚未在正式数据库执行。`0037_wallet_nonce_consumption.sql` 独立于反馈、审核和媒体对象；0031–0036 仍按 #41 → #42 → #43 → #45 → #47 的既有业务顺序处理。单独执行 0037 是待核验方案，不能假定迁移历史、生产权限或旧部署保护已经满足条件。

## 部署前

1. 核实已授权的 Supabase 项目与本站配置一致，并确认当前生产应用、可用的回退版本及执行角色。不要输出服务端密钥，也不要向浏览器提供 service role。
2. 运行同目录 `2026-11-12-wallet-nonce-preflight.sql`。表、清理索引和函数都应不存在；三个角色必须存在，执行角色应能在 `public` 创建对象并使用 `plpgsql`，`service_role` 应能使用 `public`。审查默认 ACL 和角色继承；意外结果先停止，不修改既有角色权限来绕过检查。
3. 如 `supabase_migrations.schema_migrations` 存在且可读，先核对其实际列，再只读检查 0037 是否已有记录；如不存在或不可读，记录该事实，不能当作已证明无历史。结合历史 SQL Editor 执行记录核对真实结构。不得用 `db push --include-all` 顺带执行未准备的 0031–0036，也不得用 `migration repair` 伪标未执行版本。
4. 核对应用和数据库时钟：应用接受挑战年龄最多 5 分钟及最多 5 分钟的未来时差；RPC 独立接受数据库时钟前 15 分钟至后 10 分钟。时钟异常会安全失败，先排查，不扩大窗口掩盖故障。
5. 完成隔离多连接、角色权限、故障及现有业务迁移顺序兼容检查，核对实际 SQL 的 SHA256 和独立 QA 记录。检查所有可达的旧部署/别名及其钱包验证路径：如果旧实现仍能使用相同正式 Auth 后端而绕过单次消费，不得把新版本标为完整修复。当前只对两个既有不可变部署的登录页与验证接口做过匿名 HEAD，均重定向至 Vercel SSO；其他别名、方法及授权访问仍未验证。不擅改正式凭证或外部权限。

## 数据库与应用

1. 按既有授权在确认的目标库中执行精确、已复核的 0037 事务；本迁移只创建新的 nonce 账本、索引和受限函数。事务内的权限自检发现意外授权会整体失败，不得删除检查或扩大权限强行通过。
2. 运行 `2026-11-12-wallet-nonce-postflight.sql`。确认对象存在、RLS 启用且未强制 FORCE、函数为 `security definer` 且限定 `pg_catalog` 搜索路径、表与函数 owner 一致；对照实际列、主键、约束、索引和函数定义。非内部触发器及外来外键应为零，直接表/列 ACL 只允许 owner，函数直接 ACL 只允许 owner 与 service role；结合角色继承检查 anon/authenticated 无函数执行和表/列权限，service role 有函数执行但无直接表/列权限。查询缺行或历史表不可读都不是通过。
3. 在确认的服务端连接上验证 PostgREST 能解析该函数；使用不满足格式的虚构参数应在写入前失败。不得记录或回显凭证、真实 cookie、签名或 nonce。必要时检查 schema cache，但不向旧角色授予额外权限。
4. 只有在数据库后检、PR 所有必要检查与独立 QA 完成且钱包依赖审计阻塞解决后，才可合并 PR #48。按精确 main SHA 确认 Production，再核对正式域名及受影响登录路径；真实钱包/手机与真实 Supabase 验收单独记录。

## 失败处理

- 0037 事务未提交则整体回滚；已提交但应用未发布时保留新结构和账本，旧应用不会自动获得防重放能力。新应用先于函数部署会对钱包登录返回失败，不能把此顺序用于生产。
- 新版本发生异常时优先发布保留单次消费的兼容修复；需要关闭钱包登录时通过受控应用版本关闭，而不是直接把验证路径裸退到旧实现。保留真实账本及其他历史数据。
- 消费成功但 Auth 后续失败，或 RPC 提交后响应丢失时，原挑战保持已消费，用户需重新获取挑战；存储错误不签发 OTP。不要删除单条账本记录来重试。
- 账本记录保留至少 48 小时；清理只在后续成功消费时每次最多清除 64 条过期记录，并不是定时任务。时钟异常、流量停止、长期堆积和旧部署可访问性需要运维复核。
