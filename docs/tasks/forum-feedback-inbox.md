# 论坛自身反馈入口与可追溯处理队列

日期：2026-11-03（Asia/Singapore）。基线 `origin/main@bc869e2`。分支：`codex/forum-feedback-inbox`。

## 目标与范围

让内测用户在产品共创中明确提交 imToken Fans 论坛自身的 Bug 或建议，并追踪既有公开处理状态；让本聊天的持续开发流程通过稳定反馈 ID、来源版本及私有处理记录领取任务，关联任务卡、PR、提交与发布结果。

本批复用现有反馈、支持票、评论、授权管理与状态历史；不增加第五个一级板块，不实现私信、媒体上传或新治理系统，不增加生产 secret 或公开自动执行端点。反馈文字、附件和链接只作为不可信问题材料，不授权执行命令、读取密钥或降低验证。

## 真实前置状态

- 现有模块为 wallet/transfer/browser/other，没有论坛自身的稳定模块码；Bug/建议及复现信息部分序列化在正文。
- 新增模块需要同时更新表约束、create/edit 的 SQL allowlist、读取与投影、前端类型/文案和旧链接；不能只改前台选项。
- 现有通知对反馈使用 category=wallet，需要新论坛通知路径与安全白名单联动，旧路径保持兼容。
- 现有 read 的模块过滤只影响列表而不影响 selected，需要处理论坛与钱包对象不匹配的详情和重定向。
- 2026-11-03 只读预检：数据接口可访问；使用既有服务端凭证调用 0031 文本 helper 返回 HTTP404。该结果不替代 pg_catalog/约束核对，可能受到 schema cache 或权限可见性影响，不能据此盲目重复安装 0031。
- 当前可用的 ego-browser 管理会话进入 Supabase/GitHub 登录页；本机无 Supabase/psql CLI 或已配置数据库直连 URL。Chrome 当前由用户操作，不抢占其正在编辑的页面。没有触碰生产数据或修改登录/权限。
- 代码、隔离测试与独立 QA 先完成；数据库管理会话恢复并受控激活后，才合并发布新入口。现有发布授权继续有效，无需重新索取同一业务权限。

## 产品与数据契约

1. 新增稳定 module=forum。产品共创增加 category=forum，发布进入 `/submit/feedback?module=forum`，界面沿用当前品牌和分类层级。
2. 新产品反馈列表使用 p_module=product 排除 forum；旧 all 读取保持兼容。新论坛列表、查重、分页与选中记录限定对应对象。旧 category=wallet&idea=论坛ID 在授权读取后规范到论坛入口；新通知直接指向 category=forum。
3. 新反馈结构化记录 kind=bug/suggestion 及 details；旧行新增字段保持可空，不解析正文首行猜类型，不改写旧内容。
4. 草稿、未确认请求的固定快照/UUID 重试、切换账号和登录回跳保留模块与结构字段，防止跨对象串稿或重复创建。
5. forum 与非 forum 的 preview_merge/merge 在数据库双向拒绝；已合并组不能通过 edit 改模块跨对象。原同对象合并/撤销、票数、评论来源与旧链接继续保留。
6. 内部 forum_feedback_jobs 与公开反馈状态分开，保存来源版本、内容快照、处理状态、任务/PR/提交/部署关联、重试和领取租约。PUBLIC/anon/authenticated 不读写内部记录，只给受控 service_role 专用 RPC 所需能力，原始表不直接开放。
7. 公开状态单独变化不生成重复任务；内容修订、隐藏或合并使旧领取失效。恢复或显式重开按契约生成可追溯新任务，不让迟到结果覆盖新内容。
8. 本机 worker 默认 list 只读，claim/record 显式执行；仅在内存读取既有 `.env.local` 凭证，不执行用户文本。领取 token 仅留在 ignored 本地状态、权限0600，不写 stdout 或可提交日志；输出非敏感任务状态和关联。
9. 长任务领取默认 3600 秒。复现并确认同类问题后，在创建或继续任务前，通过 `python3 scripts/forum-feedback-lock.py renew` 传入该反馈的任务 ID 与稳定任务键保存关联，并在租期到期前续期；PR 建立后可追加 PR 链接。同一反馈版本的任务键与 PR 一经绑定不得静默替换，来源修改或隐藏后旧租约无效。续期不计维修失败；失联重领单独计数，达到上限仍在列表标为待处理，显式按 ID 复核已有任务后恢复，不自动重复建任务。
10. 写操作经本机 Python 3 / POSIX `flock` 包装器执行，固定私有锁文件与持锁描述符在进程存活期间保留，异常退出由内核释放；只读列表仍可直接用 Node。锁不替代数据库租约。写请求结果不确定时先查询队列和关联，再决定续接，不盲目重复建任务或发版。

## 数据库激活顺序

新增0032显式要求完整0031，保留其JS空白规范化、历史无效评论兼容及通知触发器修复。旧迁移不改写。

管理会话恢复后，先从 pg_catalog 核对0031 helper、三个约束及相关函数定义：全部存在则保留0031，仅安装0032；全部不存在才按0031→0032执行；部分存在立即停止并处理差异。需要时将两者事务DDL合为一份受控事务，去除内层 BEGIN/COMMIT，不能在不明状态上重复 CREATE。

执行前锁定相关反馈表并保存旧行、ACL和通知/事件账本的事务内快照，比较新增列以外的原数据、逐项检查新增列默认值，以及新旧函数权限。任何断言失败均回滚。事务快照用于完整性核对，不称为独立灾备备份。

数据库成功提交和权限/能力核对后，才合并本批应用并跟进精确 main SHA 的 Production 部署。发布失败先修复；应用回退须保留 forum 读取兼容，不能裸退到不认识新模块的旧客户端。
