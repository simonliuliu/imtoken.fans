# 产品共创反馈：Canny 调研与实施建议

日期：2026-10-15。状态：调研完成，供产品 review；未实现新功能、未迁移数据库、未连接外部采集渠道。

## 结论与范围

将用户所说的 Product Cooperation Feedback 对应到现有「产品共创 → 产品反馈」。保留「社区产品」「产品公告」两个同级子区。建议在现有 Next.js / Supabase 工程内自建反馈闭环，借鉴 Canny 的收集和整理流程。直接接入 Canny 可作为快速托管方案，但需要先验证钱包账号映射、中英体验、视频文件、合并撤销、数据导出及服务成本，不能默认已满足本站 PRD。

本任务细化 [PRD](../product-requirements.md) 的 FB-01～07、NEWS-01～04，不改写已确定的首版范围。设计/开发前仍需完成阶段 review；真实业务依赖 M2 模型核对。

## Canny 能力与本站取舍

| 能力 | 官方资料说明 | 本站建议 |
| --- | --- | --- |
| 公开门户 | 提交、投票、讨论、状态跟踪和公开路线图 | 首版核心，沿用本站账号和导航 |
| 表单 | 每个 board 可定制提交文案，可配置额外字段 | 问题/建议分型；必填精简，按类型展开补充项 |
| 多渠道收集 | 门户、团队录入、客服工具、评论平台、导入及 API | 首版站内提交；后续人工录入/CSV，再按授权接具体渠道 |
| 整理与自动化 | Autopilot 提取诉求、去重并按产品领域整理 | 先人工分类/合并；AI 后续提供候选、摘要和追问草稿 |
| 追问上下文 | Smart Replies 可自动公开追问 | 首版由处理人员追问；后续 AI 先供人工审核，明确机器人身份 |
| 合并/撤销 | 携带评论和票；合并不发用户通知；链式合并有撤销限制 | 按本站 PRD 保留来源和旧链接，票按用户去重，受控撤销且通知去重 |
| 嵌入 | 可将 Canny board 通过 widget 嵌入网页/移动应用 | 自建统一来源入口；未获钱包端支持前，只交付网页入口 |

不能将渠道原始报告数视为支持人数。客服代录只代表一条来源证据，不自动伪造站内用户投票。Canny 当前收集说明也明确它可读取外部问卷结果，不应将其理解为本站首版必须自建问卷引擎。

## 页面融入

1. 首页保持现有内容流和四板块导航。反馈行显示「产品反馈」、模块、处理状态、支持数与评论数；少量精选反馈进入推荐位，避免首页变成任务后台。
2. 产品共创页保留三个子区，产品反馈采用独立业务组件。顶部「搜索已有反馈」「提交反馈」，列表提供类型、模块、状态筛选，最新/支持最多排序及「我提交/我支持」。查询条件写入 URL，便于分享和返回。
3. 反馈卡片把支持操作置于明显位置；支持代表需求，反馈不再同时强调一个含义接近的点赞数。社区产品支持仍独立计数。
4. 新建表单先给查重入口。输入标题后，首版可手动执行关键词搜索并显示同屏候选；自动联想后置。用户可支持已有反馈，或继续新建。
5. 详情主区放原始诉求、场景、附件、讨论；侧区放模块、平台/版本、状态、支持、订阅和关联更新。移动端改为顶部摘要与底部操作。状态时间线与普通评论分开，内部备注不进入公开响应。
6. 在共创区域内提供公开进展视图，复用同一批反馈记录；已完成条目链接到产品公告，不复制帖子。公开进展只展示授权确认的计划，不自动给承诺日期。

建议保留 `/community/feedback` 已有入口及旧详情链接。具体子路由在模型/页面设计批次确定，避免现在批量改 URL。

## 信息收集与处理闭环

用户路径：搜索 → 支持已有反馈/提交新反馈 → 审核 → 公开讨论与补充 → 归类/分派 → 更新状态 → 公告关联 → 通知 → 用户验证。

必填：类型（问题/建议）、标题、描述；模块提供「不确定」。建议补充目标/使用场景。问题按需补充复现步骤、预期/实际、App 版本、操作系统、网络及截图/录屏。环境字段不强制每人填写，不采集助记词、私钥、密码或资产余额；交易哈希等可能关联身份的信息不默认公开索取。附件提交前提示遮挡敏感信息。

处理状态采用 PRD：待整理 → 评估中 → 计划中 → 进行中 → 已完成；旁支需补充信息/暂不采纳。审核状态、处理状态、发布者身份及合并关系独立。社区整理人员可以整理记录，只有获授权的产品处理者能作产品排期和结果声明；尚无官方承接时准确标明社区收集，不冒充官方工单。

## 实现建议

推荐概念模型为通用内容主表 + feedback 扩展，实施前比较扩展 submissions 与新 posts 的迁移成本。候选对象：

- 内容：作者、板块、类型、正文、审核、可见性；反馈扩展保存模块、场景、环境、状态、负责人。
- 支持：用户与反馈的唯一关系；保留原始来源和取消事件，为合并/撤销提供依据。
- 订阅：与支持分开；作者、支持者、单独订阅者按一个事件去重，取消支持后按剩余订阅理由决定通知。
- 处理历史：操作者、前后值、理由、时间；内部备注单独授权。
- 来源证据：渠道、来源标识、原始引用、导入批次和访问范围；以后支持一项诉求关联多份证据。
- 媒体：归属、草稿/已绑定状态、格式、大小、时长、审核及清理期限；私有桶按权限签发短效访问链接，含访问时的内容可见性检查。
- 合并事件：来源、目标、原因、支持来源映射及撤销信息；原文和旧 URL 保留。
- 公告关联及通知发件箱：一个公告可关联多项反馈；事件与收件人唯一去重，后台重试发送。

浏览/搜索只返回当前可见内容。支持使用显式 `setSupport(id, true/false)`，避免重试将 toggle 反向执行。状态修改使用版本校验防止覆盖；合并/撤销通过受权的数据库事务和锁完成，不用多个浏览器写操作拼接。A→B、B→C 的根解析、循环检查及并发锁顺序需专门设计。受限的数据库函数须校验调用者、固定 search_path 和执行权限。

中文首版搜索可先使用参数化关键词匹配与模块过滤；不依赖默认英文分词器覆盖中文。数据量增大再评估索引和跨语言向量检索。AI 不直接执行合并、公开原始客服材料或修改处理状态。

## 交付顺序与验收

| 批次 | 交付 | 验收重点 |
| --- | --- | --- |
| A：交互原型 | 共创反馈列表、搜索/提交、详情时间线、进展视图，明确演示数据 | 中英、移动端、查重/支持/状态路径；交用户 review |
| B：真实收集（M2 前置 + M3-A） | 新模型迁移草案、权限、真实提交/搜索/支持/评论、图片和视频文件 | RLS/越权、审核前附件访问、重复提交/支持重试、上传失败和清理 |
| C：处理闭环（M3-B） | 分类/分派、状态历史、人工合并/撤销、通知和公告关联 | 票重叠去重、取消不回弹、链式/并发/撤销、旧链接/讨论完整、通知去重 |
| D：收集增强 | 运营代录/CSV、具体授权渠道、AI 建议与摘要 | 来源幂等、身份映射、私密数据隔离、人工确认、成本/误判记录 |

B/C 必须按仓库工作流启用独立风险 QA。最终首版包含真实视频文件和人工合并/撤销，不能用分批交付把必需项改为远期功能。旧 product/idea、paid/creative、历史链接和 XP 语义保留，不批量转换。原型不计入真实业务验收。

运营先明确真实反馈接收方、处理权限和可公开的回应范围。指标建议：有效反馈数、可复现比例、首次人工处理时间、待补充比例、独立支持人数、结果通知到达与完成后重开情况；不以票数直接决定优先级，不按资产量加权。
